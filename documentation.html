System at a glance

SmartSaver is a hub-and-module domestic energy system. A single ESP32 Hub owns the local automation loop and serves its own dashboard. ESP32-C3 modules add one capability each — a relay or a motion sensor — and communicate with the Hub over ESP-NOW. A separate History Server is optional; it analyses the event stream but is not part of the local control loop.

Hub

  • ESP32 DevKit with LittleFS storage.
  • Wired sensors: RCWL-0516 motion, DHT11 climate, photoresistor light, DS3231 RTC.
  • Wired actuator: active buzzer on GPIO 26.
  • Rules engine, live dashboard, manual override, pairing, parts checklist and backup are local.
  • RTC stores UTC; a configurable local offset is applied for display and time rules.

Wireless modules

  • ESP32-C3, one flashed capability per module.
  • 2-channel relay module; IN1 and IN2 are driven together.
  • RCWL-0516 motion module.
  • Discovery uses verified channel hopping across 1–11 before pairing.
  • Pairing records the module in devices.json; the identity survives a Hub reboot.

ESP-NOW in this version

ESP-NOW is unencrypted. Broadcast HELLO/ack discovery cannot use a multicast encryption key, so the pre-shared and local master keys remain defined but disabled. The radio is intended for a trusted home environment. Modules do not need the Wi-Fi router for Hub-to-module traffic.

History Server

The History Server has been reworked but is not yet fully implemented or deployed. It is intended to remain Python standard-library code with a SQLite database; the planned endpoint is https://smartsaveranalytics.me, a free domain registered through Namecheap with GitHub Education. Deployment is on hold while the design is being simplified. The local Hub, dashboard and rules do not depend on it, so there is no live savings dashboard in the current build. Savings, when implemented, are intended to be derived from appliance operating hours against a user-declared baseline and power rating — not from metered current.

Functional suitability

The degree to which the system provides functions that meet stated and implied needs, correctly and completely.

1Scope coverage.

Implemented: wired motion, climate and light sensing; RTC time; wireless discovery and pairing; relay and buzzer actuation; rule-based automation; manual override; live part state; parts checklist; backup and restore. Savings reporting is planned with the History Server but is not deployed in this build. Explicitly out of scope in this version: metered current, IR emission, servo actuation, and the unimplemented catalog parts. Those parts are labelled as future plans and cannot be selected where they would create a rule that cannot run.

2Sensor readings are filtered before automation.

Each wired sensor passes through a rolling median of three samples plus hysteresis. A transient single-sample spike is therefore not propagated directly to the rule engine. The thresholds and filter live in the sensor filter module and are applied before the registry state is updated. This is a deterministic software filter, not a statistical model.

3Pairing works without per-unit configuration and persists.

An unpaired module broadcasts HELLO. The Hub records candidates only while the pairing window is open; the user approves one and assigns a mod_id. The module’s MAC and identity are written to devices.json. On boot the Hub re-registers saved peers, and a module that reboots and returns as unpaired is silently reassigned its known identity.

4Rule evaluation is correct and deterministic.

A rule is exactly one trigger condition and one action. Rule list order is priority order. In one evaluation pass, a target that has already been actuated is skipped, so several rules targeting the same actuator produce exactly one command. Manual override suppression is checked before the priority check. Old malformed action commands are flagged and disabled rather than executed.

5Actuator state is confirmed where the hardware can report it.

Wireless actuators report their resulting state; that state is ingested and shown on the dashboard. A wired actuator cannot report for itself, so the Hub posts the resulting state from the command path. The buzzer code path is implemented, but audible output was not confirmed on the original bench module — treat audible buzzer behavior as unverified hardware evidence.

6Savings computation is defined and reproducible.

The planned History Server is designed to calculate baseline hours, actual operating hours, hours saved, kWh saved and currency saved from recorded appliance transitions, using the configured power rating, baseline behaviour and tariff. It is an event-derived estimate, not a current-meter measurement. The calculation is deterministic for a fixed event set and configuration.

7Advisory estimates are separate from actual savings.

The planned savings views distinguish measured/event-derived savings from “could have saved” advisory estimates. Advisory figures are presented as estimates rather than accounting entries. The dashboard does not silently merge the two categories.

8Results are reproducible.

Rule matching, state transitions and savings arithmetic are deterministic functions of the stored inputs. Re-evaluating the same event set with the same configuration yields the same totals. No random or learning component is used in the control or savings path.

Performance efficiency

The performance relative to the amount of resources used, under stated conditions.

9Trigger-to-command latency is appropriate.

Sensor readings are evaluated in the main loop when a new reading arrives; a satisfied rule dispatches immediately. There is no cloud round trip on the control path. No formal latency benchmark is claimed; the architectural evidence is the absence of network dependency between sensing and local actuation.

10Sampling, rules and the dashboard run concurrently.

The dashboard is served by AsyncWebServer with WebSocket state pushes; sensor polling and rule evaluation run in the main loop. History posting is moved to a worker task with a queue so a slow server does not block control. The design avoids a blocking HTTP request in the control loop; no formal concurrency benchmark is presented.

11History ingest and calculation remain practical as data grows.

Ingest is a single authenticated JSON POST; SQLite stores the event stream and the server computes savings aggregates from it. The server is designed for a single household’s event volume. No large-volume load test is claimed.

12Hub resource use is appropriate for unattended operation.

The firmware uses the ESP32’s internal flash and LittleFS; the application partition is sized for the dashboard assets and firmware. The control path does not run a cloud client. Memory and CPU were considered in the design, but no formal long-duration resource profile is presented.

13Network traffic is economical.

ESP-NOW packets are small command/state messages. The dashboard uses one WebSocket and periodic state pushes rather than polling every control. History posting is event-driven and queued; it is optional. Backups are downloaded only on request.

Reliability

The degree to which the system performs specified functions under specified conditions for a specified period.

14Continuous operation without requiring restart.

The system is intended for continuous unattended operation: the main loop services sensors, the dashboard and the post queue; configuration is loaded at boot. No formal 24-hour or multi-day soak test is claimed. Restart is required after parts changes because the wired registry is rebuilt at boot.

15A module leaving does not disturb the rest.

A module that loses power, goes out of range or is removed stops reporting; the rest of the registry continues. Rules that depend on a stale reading do not treat the old value as fresh, and the dashboard/health surfaces expose module presence and staleness. Pairing records are not deleted by a temporary loss.

16History Server outage does not stop automation.

History posting is one-way and runs in a separate worker with a bounded queue and retries. If the server is unreachable, local rules, overrides and the dashboard continue. Events may be dropped when the queue is full rather than blocking the Hub.

17Recovery after power interruption.

Configuration, parts, rules and paired devices are persisted in LittleFS and reloaded at boot; the RTC keeps time with its backup battery. Manual overrides are deliberately RAM-only and therefore clear on power loss, which is the safer behavior. No formal power-cut test matrix is claimed.

18Failures are visible rather than silent.

The Hub exposes serial diagnostics for pairing, rule firing, actuation and sensor events. The planned History Server is designed to expose system-health indicators including hub uptime, sensor staleness and module presence. The dashboard shows connection state and part state. This is operational visibility, not a certified alarm system.

19Actuator command failure is detectable.

Wireless sends return an ESP-NOW result; a module’s state report confirms the resulting state. A command that is sent but never confirmed does not silently become a confirmed state. The wired buzzer path has no independent feedback; its state is the command path’s record, and the original bench module’s audible output was not confirmed.

Usability

The degree to which the system can be used by specified users to achieve specified goals effectively, efficiently and satisfactorily.

20Initial setup is guided.

The Hub starts a setup access point with a captive portal. The page asks for the home network credentials, a dashboard password and a username; it writes config and reboots into normal mode. No account, app or cloud sign-in is required. The flow is designed for an ordinary occupant; no formal usability test with untrained participants is claimed. The open setup AP exists only during provisioning.

21Dashboard state is understandable at a glance.

Home shows one compact card per enabled part, with the current value and source/capability. Live values update over the WebSocket. The current design is the Hearth theme: parchment, flat rules, clear typographic hierarchy and no decorative charts.

22Rules can be built without protocol knowledge.

The rule editor is built from the registry. Part choices use display names, and trigger/action choices are generated from the part’s capability. The custom builder is a four-step wizard: name, trigger, action, review. Users never type packet fields or capability strings.

23Pairing is a guided page.

The Parts page places pairing first: open window, power on the module, wait for a candidate, name it, approve it. Paired modules are listed with an unpair action. The wording and ordering are designed for a non-specialist.

24Override and return-to-automation are clear.

A manual On/Off starts a visible override countdown. Rules targeting that actuator are suppressed while it is active. “Clear overrides” ends every override and the dashboard updates immediately; the next rule evaluation can act again.

25Savings views are interpretable.

The History dashboard presents savings, per-appliance contribution and cost-of-ownership progress in currency and kWh, with a plain-language summary. Figures are estimates derived from operating hours, not a utility bill or a certified meter reading.

26Status messages use plain language.

Known conditions are named in user terms: no enabled sensors, no enabled actuators, stale/missing module, override still active, invalid rule option. Serial diagnostics use technical codes, but the dashboard uses readable sentences and does not expose raw packet codes as the only explanation.

27Interface is consistent.

Home, Parts, Rules and Config share the same navigation, spacing, typography, button and feedback language. The Parts page groups pairing and the checklist together; Config uses one modal panel per job. The same Hearth styling spans the Hub and the showcase.

Security

The degree to which the system protects information and data so that access is appropriate to the level of authorisation.

28Dashboard access requires credentials.

The dashboard login validates the configured username and password and issues a session token. API and WebSocket routes require the token; the token is kept in browser session storage. There is one administrator account, not a role hierarchy.

29Unauthorised control on the same network is blocked by the dashboard login.

Normal-mode dashboard routes check the session token. The setup access point is intentionally open during provisioning only; it is not the normal control surface. There is no per-user authorisation or network segmentation in this version.

30History ingest is authenticated by a shared API key.

The planned ingest path uses a shared API key; the server would reject requests without a valid key. The key is a build-time Hub value and a server-side environment value. This is a single shared secret, not per-device identity. The path is not live in this build.

31ESP-NOW is unencrypted in this version.

This is a real limitation. Broadcast discovery cannot carry a multicast encryption key, so encryption is disabled and the pre-shared/local master keys are dormant. The mitigation is deployment on a trusted home network and a documented limitation. An evaluator should rate this limitation, not treat it as solved.

32History transport security.

No History Server is deployed in this build, so there is no live ingest path or transport to inspect. The planned endpoint is HTTPS and uses a shared API key by design; the instrument’s HTTP premise describes an earlier deployment plan. This statement cannot be demonstrated operationally until the service is deployed.

33Stored event data is protected by host access.

The planned deployment would keep SQLite data and the server process on the host. Access would be limited to parties with host access; UFW would restrict exposed services. There is no at-rest database encryption and no per-record encryption. This is appropriate only for the stated small shared deployment, not for hostile multi-tenant hosting.

Compatibility

The degree to which the system can exchange information with other systems and perform its functions while sharing an environment.

34Browser and device-size coverage.

The dashboard is a responsive single page: a 1000px desktop column, stacked mobile layout, native form controls and no browser-specific framework. It targets current Chromium, Firefox and Safari. No formal cross-browser test matrix is claimed.

35Wi-Fi and router restart behavior.

The Hub reconnects to the configured Wi-Fi after a router restart; the dashboard is served from the Hub. Wireless modules use ESP-NOW and do not depend on the router for Hub-to-module traffic. Pairing records are reloaded and peers re-registered on boot. No router-vendor matrix is claimed.

362.4 GHz coexistence.

ESP-NOW and Wi-Fi share the 2.4 GHz radio. The pairing flow uses channel hopping across 1–11 to find the Hub. No spectrum analyzer or interference benchmark is presented; the system is intended for a normal home RF environment.

37Data can be exported without loss of meaning.

The Hub offers a JSON backup containing parts, rules, paired devices and preferences. Wi-Fi and dashboard credentials are deliberately excluded. The planned History Server is designed to store events in SQLite and expose JSON views. The backup is a system restore format, not a general interoperability schema; no third-party import format is claimed.

Maintainability

The degree to which the system can be modified effectively and efficiently, including correction and improvement.

38Code is separated by responsibility.

The Hub separates the sketch/orchestration, wired drivers, sensor filtering, parts registry, rule storage, rule engine, web server, web assets and local rule catalog. The module firmware has its own capability implementations. The History Server separates ingest/database, savings, migrations, charts and dashboard rendering.

39Database schema and migrations are ordered.

The SQLite schema is created by an ordered migration mechanism; existing data is retained across schema changes. The server is single-file backed and has no ORM or third-party migration framework.

40New capability or trigger can be added locally.

The capability catalog, parts checklist and rule option table are data-driven; adding a capability requires touching the catalog, the driver dispatch and, where relevant, the rule options. Unimplemented catalog entries are deliberately disabled until their driver exists. The rule engine itself stays one-trigger/one-action.

41Behaviour is diagnosable from logs and status.

The Hub prints structured serial lines for boot, registry, pairing, sensor state, rule decisions, override and posting. The server writes systemd logs and exposes health data. The dashboard shows connection and part state. Logs are operational diagnostics, not a formal audit trail.

42Configuration is centralised where practical.

Parts, rules, pairing, time zone, buzzer preference and dashboard login are configured through the dashboard. History endpoint/API key and hardware pin assignments remain build-time values in firmware. Changing those requires a rebuild; this is a documented boundary rather than a fully code-free configuration system.

Portability

The degree to which the system can be transferred from one environment to another effectively and efficiently.

43History Server can move hosts.

The planned server uses only the Python standard library and a single SQLite file. There is no external database, package manager dependency or vendor-specific SDK. Moving it means copying the code, database, environment key and service unit to another Python host.

44Hub can be redeployed to a different room layout.

Parts, rules and paired devices are persisted data; a different room can be configured through the dashboard. The wired pin map and firmware build are constants, so a fundamentally different wiring layout still needs a firmware change.

45A module can be repurposed by reflashing.

Each module is flashed with one capability — relay or motion — and is then paired as that capability. Changing its role means reflashing the module and pairing it again; no hardware modification is required.

46The system can move to another dwelling by adding/removing modules and adjusting configuration.

Installation is Hub plus modules per room; the dashboard handles parts, pairing and rules. The registry supports a finite set of entries and the rule store has a fixed capacity, so very large installations are bounded by firmware limits rather than by a licensing or cloud tier. No multi-tenant or multi-home tenancy is implemented.

Overall and limits

These are the facts an evaluator should weigh when assigning the overall rating. They are not a recommendation.

Overall picture

SmartSaver is best described as a working local-first prototype, not a production-certified product. Its strongest evidence is the local control loop: explicit rules, live state, manual override, pairing and a dashboard that works without a cloud account. Its weakest areas are the documented security limitations, the absence of metered current, and the lack of formal long-duration, load and cross-browser testing. Those are known boundaries, not hidden defects.

Strong evidence

  • Local rule execution with no cloud dependency on the control path.
  • Explicit one-trigger/one-action rules, priority order and override suppression.
  • Registry-driven dashboard, parts checklist, pairing and rule editor.
  • Persistent parts, rules, pairing and preferences across reboot; backup/restore around them.
  • Deterministic, inspectable savings arithmetic with a separate advisory estimate.

Known limitations

  • ESP-NOW is unencrypted in this version; the broadcast-discovery constraint is documented and the deployment is trusted-network only.
  • No metered current: savings are derived from appliance operating hours and a declared baseline, not measured power.
  • One trigger, one action: compound conditions and release actions are not supported.
  • Single administrator: no roles, per-user permissions or audit trail.
  • Buzzer feedback: the code path exists, but audible output was not confirmed on the original bench module.
  • Unimplemented parts are catalog-only future plans; they are disabled and cannot be treated as available hardware.
  • No formal long-duration soak, load, cross-browser or power-cut test matrix is claimed.

What can be inspected in the showcase

Software: provisioning and login, live part state, manual override, parts checklist, pairing, predefined rules, four-step custom rule wizard, config and backup.

Hardware: Hub, relay modules, wireless motion module and the currently tested Hub sensors: RTC, motion, climate and light.
